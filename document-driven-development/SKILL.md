# 文档驱动开发

提供快速档、标准档和复杂档。在档位未被用户指定时，根据改动范围选择：影响范围清晰的日常小缺陷或局部修正使用快速档；已规划、需要持续跟踪的功能改动使用标准档；跨多个模块或服务、存在多轮现场需求或手工测试反馈的复杂改动使用复杂档。

## 记录原则

`progress.md` 是按时间追加的事实日志。完成实际修改、形成关键决策、发现风险或出现阻塞后，新增带日期的条目，如实记录当时发生的情况；不要为了反映后续状态而改写、删除或重排既有记录。

若早期记录需要纠正，新增一条说明被纠正的记录、原因和正确事实，并关联原记录日期。`plan.md` 则只保留当前有效方案；用它回答“现在按什么做”，用 `progress.md` 回答“过程里发生了什么”。

## 分层记忆与跨会话接续

以下规则适用于三个档位。影响后续工作的状态和结论应落盘，使新会话无需依赖旧聊天记录即可继续。

### 1. 按生命周期保存

- 任务状态：保存在本次变更目录，包含当前方案、实际进展、关键证据和待办；结束后按“完成与归档”处理。
- 会话中间结果：临时推演、重复输出和探索草稿无需长期保存；影响下一步的结论、失败原因和必要证据应提炼进任务记录。只清理确认不再需要的代理临时文件，保留用户文件及未完成成果。
- 长期记忆：稳定的项目约定放项目常驻规则（如 `AGENTS.md`），通用开发方法放技能。仅在用户授权维护相应规则时沉淀，保留适用范围；单次任务状态留在变更目录。技能按需加载，文件存在不代表当前会话已读取。

### 2. 追加接续记录

每个阶段结束、暂停或转交前，在 `progress.md` 末尾追加带日期和时间的接续记录；快速档写入 `change.md` 的“实施记录”。实质进展及时落盘，不等到会话结束；阶段日志已含以下信息时无需重复另写。

- 当前阶段与状态：进行中、受阻、待用户验证或已完成。
- 已完成的工作、已执行检查及其结果；待验证内容单独列明。
- 阻塞、关键待决事项，以及下一步可直接执行的动作。
- 工作位置：工作根目录约定、相关文件相对路径；Git 仓库记录分支、当前提交、未提交改动及已知归属，非 Git 项目标明不适用。跨仓库时分别记录。

旧记录保持原样，后续状态通过新条目说明。恢复不依赖工作区干净或所有改动已提交。

### 3. 从文件恢复

新会话接手或上下文缺失时，先定位本次变更目录，沿用已有档位和文档；有多个无法区分的活跃任务时确认目标。

依次读取项目常驻规则、当前 `plan.md`（快速档为 `change.md`）、最新接续记录，以及存在的 `handoff.md`。复杂档按需追溯关联调整和测试记录，无需重读全部历史。

随后核对相关代码、Git 状态和近期提交。文档记录可能滞后，发现差异先确认并追加事实记录；以用户最新要求确定目标，不能仅凭旧日志认定工作已完成。确认当前目标、实际状态和下一步后继续。

### 4. 保留可复现入口与版本线索

在方案或快速改动单中引用项目已有启动、环境准备和验证入口，补充必要的工作目录、依赖条件及环境变量名称；密钥不写入记录。只有现有入口不足且本次任务确有需要时才新增启动脚本，并注明验证情况。

用 Git 历史辅助定位实现和恢复基线；提交、推送按用户授权执行。任务记录与代码一起纳入版本管理时，遵循仓库约定；暂停不自动触发回滚、清理或提交。

## 快速档

适用于目标明确、改动范围小、无需持续排查或多方协作的日常修复。目标是保留可追溯性，同时不让文档成本超过改动本身。

### 1. 创建一页改动单

用户确认开始开发后，在约定的变更记录根目录下创建日期加简洁改动名称的目录。默认只创建 `change.md`，不拆分 `plan.md`、`progress.md` 和 `outcome.md`。

`change.md` 使用以下结构：

```md
# 本次改动背景与总览

## 问题与目标

## 最小改动方案

## 实施记录

## 验证与结果
```

所有路径相对于约定的工作根目录书写，确保文档可分享和复用。

### 2. 轻量实施记录

编码前填写“问题与目标”和“最小改动方案”。实施过程中仅在方案发生偏差、发现影响范围变化或出现阻塞时，在“实施记录”中按日期追加事实记录；保留初始方案，以便看出实际选择的原因。

完成后填写“验证与结果”，如实说明实际改动、手工测试方式、测试结果、影响范围和遗留事项。用户保留手工测试时，提供精确用例，不执行未获授权的功能测试。

仅在工作暂停或转交时创建 `handoff.md`，引用最新接续记录，补充剩余工作、手工测试用例和可直接转发的话术。

## 标准档

### 1. 固化方案

用户确认开始开发后，在约定的变更记录根目录下创建本次变更目录。目录名使用日期加简洁的改动名称。

创建并维护以下文档：

- `plan.md`：已确认的方案和验收标准。
- `progress.md`：带日期的实际排查、决策、修改和检查记录。
- `outcome.md`：最终交付的改动、可观察行为、验证结果和已知限制；不用于记录交接。

每份文档均以**本次改动背景与总览**开篇。路径相对于约定的工作根目录书写，确保文档可共享。

仅在工作暂停或转交时创建 `handoff.md`。其中引用最新接续记录，补充剩余工作、实现切口、手工测试用例和可直接转发的话术。

### 2. 按方案实施

修改前核对真实入口、调用方、既有约定和工作区状态。无关改动视为用户已有内容。

以满足方案的最小完整改动为准。当新增的领域流程会继续拉长大型入口文件时，将其放入聚焦模块；入口文件仅作为路由、上下文解析和传输适配层。新模块通过参数接收依赖，不反向导入入口文件。

每次形成实质决策或完成实际修改后，在 `progress.md` 追加带日期的事实记录，不记录纯猜测。用户变更需求时，同步更新当前方案；既有进度记录保持原样。

### 3. 验证与交付

验证范围遵循用户授权和仓库约定。若用户保留手工测试，提供精确的手工用例，不执行未获授权的功能测试。

完成后在 `outcome.md` 写入实际修改的文件、行为、已执行检查和剩余限制；不得将计划中的工作描述为已完成。

若用户停止或转交工作，保留可接续的未完成修改，在 `handoff.md` 和 `progress.md` 中标明实验性内容、风险和转交状态。确需回滚时依据用户授权，仅处理已确认归属的改动。

## 复杂档

适用于跨模块或服务、分阶段实施，且可能因现场需求或多轮手工测试反复调整的改动。复杂档在标准档基础上默认增加 `adjustments.md`，用于把变化的原因和当前方案分开管理。

### 1. 创建并维护文档

创建并维护以下文档：

- `plan.md`：当前生效的方案、分阶段实施、验收条件、关键约束和风险考虑。
- `adjustments.md`：现场需求或测试反馈引起的调整，按时间追加。
- `progress.md`：按里程碑记录实施状态、阻塞和风险。
- `outcome.md`：最终改动、验证证据、影响范围和遗留事项。

每份文档均以**本次改动背景与总览**开篇，路径相对于约定的工作根目录书写。仅在暂停或转交时创建 `handoff.md`。

当测试轮次很多、参与者较多或需要明确回归清单时，额外创建 `test-matrix.md`；其他情况下，将复测方式和结果写在对应的 `adjustments.md` 条目中。

### 2. 让方案与调整各自保持单一职责

`plan.md` 只反映当前有效方案，不保留被替代的细节。每次现场需求或手工测试导致行为、范围、接口、数据或验收方式变化时，先在 `adjustments.md` 新增条目，再同步更新 `plan.md`。

每条调整至少记录日期、来源、现象或诉求、处理决定、影响范围、关联的方案章节、复测方式与结果、当前状态。这样可以同时回答“现在按什么做”和“为什么改成这样”。

`progress.md` 只跟踪里程碑状态，不重复调整细节；`outcome.md` 最终汇总已完成的调整及其验收证据。

### 3. 按里程碑实施与验证

将复杂改动拆成可独立验收的里程碑。每个里程碑开始前确认当前 `plan.md`，完成后更新 `progress.md`，并按用户授权提供或执行验证。用户负责手工测试时，给出可复现的测试步骤；测试反馈进入 `adjustments.md`，再驱动下一轮方案和代码修改。

当单一子系统的设计使 `plan.md` 难以阅读时，按需拆出 `design-<主题>.md`，而不是预先创建空文档。

## 完成与归档

当成果符合当前方案、所需验证已有明确结果，且文档反映真实状态时，记录已完成。用户负责的验收尚未反馈时，写明“开发完成，待用户验证”；暂停或交接不等于任务完成。

在 `outcome.md`（快速档为“验证与结果”）记录最终成果、验证证据和遗留事项，并追加最终接续记录。任务关闭后保留原变更目录作为归档；若项目已有活跃任务索引，更新对应状态。归档不要求移动或删除目录，后续会话仅在相关任务需要时读取。

归档任务再次发生调整时，追加重开原因和新状态，再更新当前方案，保留原完成记录。
