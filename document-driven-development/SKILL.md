# 文档驱动开发

提供快速档、标准档和复杂档。优先遵循用户指定的档位；未指定时，根据改动范围选择：简单的一次性代码或文档编辑、影响范围清晰的日常缺陷修复或局部修正使用快速档；需要持续跟踪的功能改动使用标准档；跨多个模块或服务、存在多轮现场需求或手工测试反馈的复杂改动使用复杂档。

## 记录原则

原始目标、当前进度和关键结果分别维护在固定分区中，不依赖聊天记录或从历史日志中重新拼凑。

`plan.md` 在背景总览后分为“原始目标与验收基线”和“当前执行方案”。前者保留最初确认的目标、范围和验收条件；后者维护当前生效的目标、方案和验收条件。只有用户明确变更目标时才调整当前目标，并在过程日志（复杂档为 `adjustments.md`）记录来源、原因及与原始基线的差异，保留原始基线。

`progress.md` 在背景总览后依次设置以下分区：

- 当前状态：维护更新时间、当前阶段、子任务清单（稳定编号、内容、状态）、阻塞与待决事项、下一步动作及工作位置。子任务状态区分待办、进行中、受阻、待验证、已完成。
- 关键结果：使用固定字段的表格或条目，记录结果编号、结论、证据位置、验证状态（待验证、已验证或已失效）、影响及更新时间。按编号更新最新结论，证据引用相关文件、检查记录或提交；没有结果时标明暂无，不填充猜测。
- 过程日志：按时间追加排查、决策、修改、检查和接续记录，保留当时事实。发生关键结果修正或失效时，先追加原因和证据，再更新对应结果。

“当前状态”和“关键结果”可更新；“过程日志”不因后续变化而改写、删除或重排。早期日志有误时，追加纠正说明并关联原记录日期。迁移已有文档时保留原日志正文，在前部补充分区。快速档在 `change.md` 中维护同样的目标、状态和结果分区，“实施记录”承担追加日志职责。

## 分层记忆与跨会话接续

以下规则适用于三个档位。影响后续工作的状态和结论应落盘，使新会话无需依赖旧聊天记录即可继续。

### 1. 按生命周期保存

- 任务状态：保存在本次变更目录，包含当前方案、实际进展、关键证据和待办；结束后按“完成与归档”处理。
- 会话中间结果：临时推演、重复输出和探索草稿无需长期保存；影响下一步的结论、失败原因和必要证据应提炼进任务记录。只清理确认不再需要的代理临时文件，保留用户文件及未完成成果。
- 长期记忆：稳定的项目约定放项目常驻规则（如 `AGENTS.md`），通用开发方法放技能。仅在用户授权维护相应规则时沉淀，保留适用范围；单次任务状态留在变更目录。技能按需加载，文件存在不代表当前会话已读取。

### 2. 追加接续记录

实质进展或关键结果变化后，及时更新当前状态与关键结果。每个阶段结束、暂停或转交前，在 `progress.md` 的“过程日志”末尾追加带日期和时间的接续记录；快速档写入 `change.md` 的“实施记录”。阶段日志已含以下信息时无需重复另写，关键结果可引用结果编号和证据位置。

- 当前阶段与状态：进行中、受阻、待用户验证或已完成。
- 已完成的工作、已执行检查及其结果；待验证内容单独列明。
- 阻塞、关键待决事项，以及下一步可直接执行的动作。
- 工作位置：工作根目录约定、相关文件相对路径；Git 仓库记录分支、当前提交、未提交改动及已知归属，非 Git 项目标明不适用。跨仓库时分别记录。

历史日志保持原样，当前状态区同步反映最新情况。恢复不依赖工作区干净或所有改动已提交。

### 3. 从文件恢复

新会话接手或上下文缺失时，先定位本次变更目录，沿用已有档位和文档；有多个无法区分的活跃任务时确认目标。

依次读取项目常驻规则、`plan.md` 的原始目标与当前执行方案、`progress.md` 的当前状态与关键结果、最新接续记录，以及存在的 `handoff.md`。快速档读取 `change.md` 的对应分区；复杂档按需追溯关联调整和测试记录，无需重读全部历史。

每轮开始实际工作、恢复会话或调整方案前，核对原始目标、用户已确认的目标变更和当前验收条件，确认下一步仍服务于目标；只有发现偏离或需要说明取舍时才向用户解释，无需每条回复重复目标。

随后核对相关代码、Git 状态和近期提交。文档记录可能滞后，发现差异先确认并追加事实记录；以用户最新要求确定目标，不能仅凭旧日志认定工作已完成。确认当前目标、实际状态和下一步后继续。

### 4. 保留可复现入口与版本线索

在方案或快速改动单中引用项目已有启动、环境准备和验证入口，补充必要的工作目录、依赖条件及环境变量名称；密钥不写入记录。只有现有入口不足且本次任务确有需要时才新增启动脚本，并注明验证情况。

用 Git 历史辅助定位实现和恢复基线；提交、推送按用户授权执行。任务记录与代码一起纳入版本管理时，遵循仓库约定；暂停不自动触发回滚、清理或提交。

### 5. 与运行环境的上下文恢复能力协同

当运行环境已提供上下文恢复能力时，沿用其机制；本技能仍负责将项目目标、状态、关键结果和验收证据维护在变更目录中。无需为了使用本技能调整该功能的开关；环境未提供恢复能力时，仍按“从文件恢复”接续。

恢复后读取本次变更目录的必要分区并核对实际工作区，按需追溯历史。自动恢复成功不代表项目文档已更新，也不是任务完成或验收通过的证据。

信息不一致时，按类型处理：目标和范围以用户最新明确要求为准，并补入当前方案及变更依据；完成情况以相关代码、Git 状态和验证证据核实，再更新状态与关键结果；历史过程保留旧日志，通过追加条目说明差异。

项目文档集中维护完整开发记录，其他接续材料按需引用变更目录、结果编号或证据位置，避免重复维护完整台账。单纯的上下文切换不视为工作暂停或转交，不因此新建 `handoff.md`；仍按实质进展和阶段节点及时落盘。

## 快速档

适用于目标明确、改动范围小、无需持续排查或多方协作的日常修复。目标是保留可追溯性，同时不让文档成本超过改动本身。

### 1. 创建一页改动单

用户确认开始开发后，在约定的变更记录根目录下创建日期加简洁改动名称的目录。默认只创建 `change.md`，不拆分 `plan.md`、`progress.md` 和 `outcome.md`。

`change.md` 使用以下结构：

```md
# 本次改动背景与总览

## 原始目标与验收基线

## 当前执行方案

## 当前状态

## 关键结果

## 实施记录

## 验证与结果
```

所有路径相对于约定的工作根目录书写，确保文档可分享和复用。

### 2. 轻量实施记录

编码前填写“原始目标与验收基线”和“当前执行方案”，方案以最小完整改动为准。实施中更新当前状态和关键结果；出现方案偏差、影响范围变化、阻塞或关键结果修正时，在“实施记录”中按日期追加事实记录，阶段结束时按接续规则记录。

完成后填写“验证与结果”，如实说明实际改动、手工测试方式、测试结果、影响范围和遗留事项。用户保留手工测试时，提供精确用例，不执行未获授权的功能测试。

仅在工作暂停或转交时创建 `handoff.md`，引用最新接续记录，补充剩余工作、手工测试用例和可直接转发的话术。

## 标准档

### 1. 固化方案

用户确认开始开发后，在约定的变更记录根目录下创建本次变更目录。目录名使用日期加简洁的改动名称。

创建并维护以下文档：

- `plan.md`：原始目标与验收基线、当前执行方案。
- `progress.md`：当前状态、结构化关键结果和追加式过程日志。
- `outcome.md`：最终交付的改动、可观察行为、验证结果和已知限制；不用于记录交接。

每份文档均以**本次改动背景与总览**开篇。路径相对于约定的工作根目录书写，确保文档可共享。

仅在工作暂停或转交时创建 `handoff.md`。其中引用最新接续记录，补充剩余工作、实现切口、手工测试用例和可直接转发的话术。

### 2. 按方案实施

修改前核对真实入口、调用方、既有约定和工作区状态。无关改动视为用户已有内容。

以满足方案的最小完整改动为准。当新增的领域流程会继续拉长大型入口文件时，将其放入聚焦模块；入口文件仅作为路由、上下文解析和传输适配层。新模块通过参数接收依赖，不反向导入入口文件。

每次形成实质决策或完成实际修改后，更新 `progress.md` 的当前状态和相关关键结果，在过程日志追加带日期的事实记录。用户变更需求时，按记录原则更新当前方案并保留变更依据。

### 3. 验证与交付

验证范围遵循用户授权和仓库约定。若用户保留手工测试，提供精确的手工用例，不执行未获授权的功能测试。

完成后在 `outcome.md` 写入实际修改的文件、行为、已执行检查和剩余限制；不得将计划中的工作描述为已完成。

若用户停止或转交工作，保留可接续的未完成修改，在 `handoff.md` 和 `progress.md` 中标明实验性内容、风险和转交状态。确需回滚时依据用户授权，仅处理已确认归属的改动。

## 复杂档

适用于跨模块或服务、分阶段实施，且可能因现场需求或多轮手工测试反复调整的改动。复杂档在标准档基础上默认增加 `adjustments.md`，用于把变化的原因和当前方案分开管理。

### 1. 创建并维护文档

创建并维护以下文档：

- `plan.md`：原始目标与验收基线，以及当前生效的方案、分阶段实施、验收条件、关键约束和风险考虑。
- `adjustments.md`：现场需求或测试反馈引起的调整，按时间追加。
- `progress.md`：当前子任务与里程碑状态、关键结果，以及按里程碑追加的过程日志。
- `outcome.md`：最终改动、验证证据、影响范围和遗留事项。

每份文档均以**本次改动背景与总览**开篇，路径相对于约定的工作根目录书写。仅在暂停或转交时创建 `handoff.md`。

当测试轮次很多、参与者较多或需要明确回归清单时，额外创建 `test-matrix.md`；其他情况下，将复测方式和结果写在对应的 `adjustments.md` 条目中。

### 2. 让方案与调整各自保持单一职责

`plan.md` 的“当前执行方案”只反映当前有效方案；“原始目标与验收基线”保持保留。每次现场需求或手工测试导致行为、范围、接口、数据或验收方式变化时，先在 `adjustments.md` 新增条目，再同步更新当前执行方案。

每条调整至少记录日期、来源、现象或诉求、处理决定、影响范围、关联的方案章节、复测方式与结果、当前状态。这样可以同时回答“现在按什么做”和“为什么改成这样”。

`progress.md` 更新受影响的状态与关键结果，过程日志引用调整条目，不重复调整细节；`outcome.md` 最终汇总已完成的调整及其验收证据。

### 3. 按里程碑实施与验证

将复杂改动拆成可独立验收的里程碑。每个里程碑开始前确认当前 `plan.md`，完成后更新 `progress.md`，并按用户授权提供或执行验证。用户负责手工测试时，给出可复现的测试步骤；测试反馈进入 `adjustments.md`，再驱动下一轮方案和代码修改。

当单一子系统的设计使 `plan.md` 难以阅读时，按需拆出 `design-<主题>.md`，而不是预先创建空文档。

## 完成与归档

当成果符合当前方案、所需验证已有明确结果，且文档反映真实状态时，记录已完成。用户负责的验收尚未反馈时，写明“开发完成，待用户验证”；暂停或交接不等于任务完成。

在 `outcome.md`（快速档为“验证与结果”）记录最终成果、验证证据和遗留事项，同步当前状态及关键结果，并追加最终接续记录。任务关闭后保留原变更目录作为归档；若项目已有活跃任务索引，更新对应状态。归档不要求移动或删除目录，后续会话仅在相关任务需要时读取。

归档任务再次发生调整时，追加重开原因和新状态，再更新当前方案，保留原完成记录。
